# Documentation standards

How Hospitia's documentation is organized, written and kept correct. Follow this page whenever you add or change documentation.

## Where documentation lives

| What | Where |
|---|---|
| All project documentation | `hospitia-master/docs/`, built with MkDocs Material (`mkdocs.yml`) |
| Project landing page | `hospitia-master/README.md` |
| Community files | `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `SECURITY.md` in `hospitia-master` (short pointer copies in the other repositories) |
| Changelog | `hospitia-master/CHANGELOG.md` (one for the whole product) |
| Repository and service READMEs in `hospitia-frontend` / `hospitia-backend` | **Short stubs only**: purpose, port, run and test commands, and a link to the docs page. No other content. |
| Rules for AI coding agents | `hospitia-master/.agents/rules/`, linking to these pages; see [AI coding agents](ai-agents.md) |

Don't add documentation anywhere else. In particular, don't grow the stub READMEs: put the content in `docs/` and link to it.

## Choosing the section (Diátaxis)

Every page has one job. Put it in the section that matches:

| Section | Type | Answers |
|---|---|---|
| `tutorials/` | Tutorial | "Teach me": a complete walkthrough for learning |
| `guides/` | How-to | "How do I…?": steps for one task |
| `reference/` | Reference | "What is…?": facts, tables, generated API |
| `architecture/`, `about/` | Explanation | "Why / how does it work?" |
| `standards/` | Rules | "What must I do?" |
| `getting-started/` | Onboarding | Setup in order |
| `backend/`, `frontend/` | Area overviews | One page per service or area |
| `operations/` | Operations | CI/CD, deployment, observability, releases |
| `adr/` | Decision records | Why we decided something |

Don't add a new top-level section without updating this table and `mkdocs.yml`.

## Adding a page

1. Create the Markdown file in the right section, with a lowercase kebab-case name (`database-migrations.md`).
2. Add it to `nav` in `mkdocs.yml`. The strict build fails on pages missing from the nav.
3. Link to it from the section's `index.md` and from related pages.
4. Preview and check (see below).

## Writing style

- **One H1** per page, then a one or two sentence introduction saying what the page covers and who it's for.
- Write plainly, in the second person ("you"), in English, in the present tense. Use the [Glossary](../about/glossary.md) terms.
- Prefer numbered steps for procedures and tables for facts.
- Every fact comes from the code. Cite paths in backticks (`backend/services/booking/booking/api/dependencies.py`). When intent or a business fact is unknown, write a visible TODO instead of guessing:

    ```markdown
    !!! note "TODO"
        Owner to confirm …
    ```

- Don't duplicate content: link to the page that owns the topic.
- Diagrams use Mermaid code blocks (` ```mermaid `), which GitHub also renders.
- Keep pages focused; around 400 lines is a soft limit. Split longer topics.
- Admonitions (`!!! note`) and tabs (`=== "Tab"`) are allowed; they remain readable as plain text on GitHub.

## Links

- Between docs pages: **relative links** to the `.md` file (`../guides/debugging.md#frontend`). The strict build checks them, including anchors.
- To root files (`CONTRIBUTING.md`, `CHANGELOG.md`, …) or files in other repositories: absolute GitHub URLs (`https://github.com/smit9924/hospitia-master/blob/main/CONTRIBUTING.md`), because they're outside `docs/`.
- Code paths are written as inline code, not links.

## Secrets

Never put secrets, tokens, real passwords, private keys or `.env` values in documentation. Document configuration by **name and purpose** only. Local-development credentials that are already in committed sample files may be shown on local-development pages, labelled "local development only".

## Generated content

- `docs/reference/api/*.openapi.json` is generated by `bash scripts/export_openapi.sh`. Never edit it by hand; regenerate it after changing routes, schemas or dependencies, and commit it with the code change.
- `CHANGELOG.md` is included into the site by `docs/changelog.md`; edit the root file.

## Preview and check

```bash
# live preview at http://127.0.0.1:8000
uv run --no-project --with-requirements docs/requirements.txt mkdocs serve

# strict check before a pull request (also checks agent rules and skills)
bash scripts/check_docs.sh
```

Docs dependencies are pinned in `docs/requirements.txt`. Update them deliberately and run the check afterwards.

## Changelog entries

Add an entry to `[Unreleased]` in `CHANGELOG.md` for every user-visible or operator-visible change:

- Group under **Added**, **Changed**, **Deprecated**, **Removed**, **Fixed** or **Security** ([Keep a Changelog](https://keepachangelog.com/en/1.1.0/)).
- Start with the area tag: `[frontend]`, `[backend:<service>]`, `[infra]` or `[docs]`.
- Describe the change for users and operators, not the implementation; one entry per change, not per commit.
- End with a reference: the pull request (`frontend#6`, `backend#5`, `master#12`) or a short commit SHA.

```markdown
### Added
- [backend:booking] Rooms with number, floor, room type and status. (backend#5)
```

## Keeping docs in sync

Docs drift when code changes without them. Two habits prevent that:

1. **Update docs with the change.** Every pull request that changes behaviour, APIs, configuration, structure or conventions updates the affected pages and adds a changelog entry.
2. **Run `/doc-sync`.** The `doc-sync` agent skill (`.agents/skills/doc-sync/`) finds everything that changed in the three repositories since the last sync point, updates the docs, the API reference, the `[Unreleased]` changelog, the agent rules and the README stubs, runs `scripts/check_docs.sh`, and advances the sync point. It never commits: review its report and diff, then commit. Run it after merging features and before opening a pull request. With other agents, follow `.agents/skills/doc-sync/SKILL.md` as plain instructions.

Useful variants: `/doc-sync --dry-run` (report only), `/doc-sync --repo backend` (one repository).

Review the result like any other change: the skill takes facts only from the code and marks unknowns as TODOs, but it can still misread intent.

## Sync state

`docs/.sync-state.json` records the commit of each repository that the docs were last brought up to date with:

```json
{
  "updated": "YYYY-MM-DD",
  "repos": {
    "master": "<full commit SHA>",
    "frontend": "<full commit SHA>",
    "backend": "<full commit SHA>"
  }
}
```

The `doc-sync` skill reads it as the starting point and updates it after a successful run; update it by hand only after checking that the docs match all three repositories at those commits. Commits after the recorded SHA that only change the docs or the sync tooling are expected and count as "no doc impact". The file is excluded from the built site.
