# Backend standards (Python / FastAPI)

Rules for code in `hospitia-backend/services/`. The [Backend overview](../backend/index.md) describes the structure they refer to.

## Service layout

- Each service is `backend/services/<service>/` with the application package `<service>/<service>/` (for example `backend/services/auth/auth/`).
- Use the standard package map: `api/` (routes, services, repositories, dependencies), `core/` (config, security, settings), `database/` (Alembic and SQLModel models), `exceptions/` (definitions, handlers, registry), `messaging/` (base abstraction and `rabbitmq/`), `schemas/` (Pydantic request, response and message schemas), `types/` (shared types, enums, constants, error codes), plus `handlers/` for message consumers.
- The notification service has no HTTP API: its entry points are message handlers, with `services/`, `templates/` and `channels/` instead of `api/`.

## Layering

```text
API routes → services → repositories → SQLModel models → PostgreSQL
```

- **Routes** validate input, call services and return responses. No heavy business or database logic in routes.
- **Repositories** own persistence; **services** own business rules.
- Declare access on every route with the existing dependencies (`RoleValidationDep`, `ActiveOrganizationDep`, `OrganizationScopedActorDep`, `InternalRequestDep`). Never authorize by hand inside a route.

## Cross-cutting

- **Exceptions:** define in `exceptions/definitions/`, handle in `exceptions/handlers/`, register through `exceptions/registry.py` at startup, and document the response in `doc/` and the route's `responses=`. Raise from services or repositories, not routes. Never reuse or renumber an error code.
- **Messaging:** publish and consume through the MQ abstraction (`messaging/`); never use RabbitMQ clients (`pika`) in business code, handlers or services.
- **Schemas and types:** Pydantic schemas in `schemas/`, extending `BaseSchema` (camelCase JSON aliases); shared constants and enums in `types/`.
- **Configuration:** settings in `core/config.py`, values from `.env`; add new keys to `.sample.env` and `.sample.cloud-dev.env`.

## Message handlers (consumers)

- Add new message flows as handlers that delegate to `services/`; keep queue wiring out of business logic.
- Handlers validate the message against its schema and must be idempotent.
- Every consumed queue has a dead-letter queue and a retry count.

## Notification content

- Render content with Jinja templates under `templates/`; don't hard-code email bodies in Python.
- Keep exception definitions centralized under `exceptions/`.

## Models and migrations

- Every SQLModel/SQLAlchemy `Relationship()` field **must** have an explicit scalar foreign-key column on the same model, for example:

    ```python
    organization_id: int = Field(foreign_key="organizations.id", nullable=False, index=True, ondelete="RESTRICT")
    organization: Organization = Relationship()
    ```

    Keep the scalar column available for direct filtering and navigation, configure its nullability and delete behaviour to match the relationship, and include the constraint in the corresponding Alembic migration. Never rely on `Relationship()` alone to enforce referential integrity.
- Schema changes go through Alembic under `database/`. Review autogenerated migrations and make `downgrade()` reverse `upgrade()`. See [Database migrations](../guides/database-migrations.md).
- Expose `guid`s in APIs, never integer `id`s. Prefer deactivation (`is_active`) to deleting rows.

## Logging

- Use `log = logging.getLogger(__name__)`; never `print` (ruff `T201`).
- Don't log secrets, tokens, passwords or OTPs.
- In production, log JSON to stdout only.

## Style

- Python 3.13, type hints on public functions.
- Ruff must pass (`uv run ruff check .`); the rules are in each service's `pyproject.toml`.
- Docstrings follow the existing numpy-like style (Description, Parameters, Returns, Raises) used across the services.
- Manage dependencies with uv (`uv add`, commit `uv.lock`).
